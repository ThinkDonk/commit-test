# 阶段：范围确定与影响分析

## 1. 确定范围

优先级从高到低：

1. **显式范围**：用户给了就用（`HEAD~5..HEAD`、分支名、起止 commit）
2. **基线增量**：读 `projects/<项目名>/tested-commits.md` 里的基线 commit，测 `基线..HEAD`
3. **无基线**：问用户"从哪个提交开始测"，不要自作主张全量

tested-commits.md 格式：

```
# 已验证基线

- 基线: <commit-hash>（yyyy-MM-dd）
- 历史: <commit-hash> <一句话描述>
```

## 2. 拿改动文件

```bash
git diff --name-only <base>..HEAD
```

按**文件最终态**聚合处理：中间提交删掉又加回的文件只看最终状态，不逐提交分析——要验证的是现在的代码，不是历史过程。

未提交的工作区改动默认不纳入范围（基线是 commit 语义）；用户明确要求时用 `git diff HEAD --name-only` 补充。

## 3. 文件 → 模块匹配

读 `modules/` 下所有模块文件的「触发范围」字段（glob 路径模式），对每个改动文件：

- 命中某模块的路径模式 → 该模块进入测试清单
- 是后端代码但无任何模块命中 → 进「降级验证」清单
- 是文档/注释类文件 → 报告里列为"无需测试"

多模块命中同一文件是正常的（分层依赖上下游共享实体），都测。

## 4. 分类输出

| 分类 | 处理 |
|------|------|
| 命中模块 | 进 execute 阶段，按模块文件走浏览器流程 |
| 后端无页面入口（Job、OpenService、SDK 引用等） | 降级：build 通过 + 服务能启动 + 日志无异常，报告注明 |
| 前端改动但模块文件缺失 | 进 execute 阶段走"现场探索"分支，探索完沉淀新模块文件 |
| 未覆盖（无法归类） | 明确报告"未覆盖、已跳过"，列出文件，让用户决定 |

匹配结果和完整分类要写进最终报告，任何改动文件都不许静默丢弃。
