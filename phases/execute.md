# 阶段：执行、证据与沉淀

## 浏览器能力

查看当前宿主实际提供的浏览器工具及文档，遵循其初始化、标签页和读取/操作规则。已安装且适用的 `computer-use`、`web-gui-tester` 或 `control-browser` 可以辅助，不硬依赖某个技能名或不存在的 Skill 工具。

有浏览器能力就按实际工具执行。确实不可用时标明页面验证受阻，可继续已授权的其他检查；API、脚本、构建不能冒充浏览器测试。浏览器中涉及业务数据的创建、修改、删除仍遵循本次授权和受控数据范围。

## 场景执行

按分析阶段的场景清单执行必要 P0 与变更验收，不用页面能打开、toast 成功替代结果判断。模块知识不存在或入口失效时先按调用链现场探索，记录可重复的步骤和数据前提；确认有效后更新模块，探索过程本身满足验收时不机械重跑整套流程。

证据与要证明的行为对应：

| 验证目标 | 需要观察的结果 |
|----------|----------------|
| 页面入口/P0 | 目标页面、关键控件与主流程响应；不能扩展为数据或保存正确 |
| 配置、查询、计算 | 独立预期与实际数据/数量/字段；如生成 JSON、SQL 等，还需核对内容和参数绑定。记录基线已有差异与新增差异 |
| 保存与持久化 | 保存后重新读取或关闭重开，核对内容、状态和受影响对象；只看提示或仍留在内存的表单不够 |
| 失败、取消、兼容 | 错误出现的时点、应阻止的动作、取消前后/旧数据前后是否改变 |

页面场景保留实际看过的截图，并配合必要的请求/响应、数据比较或日志证据；截图不能替代不可见的数据断言，日志也不能替代页面操作。沿项目现有 artifact 目录保存，run 使用可解析的路径/链接，避免把敏感数据复制进报告。

历史补录只引用已有证据，区分原始文件、当时记录和本次复验。截图或原始输出缺失就写“未留存/未核实”，不能用后来截图假冒历史现场。

## 发现问题与修复

先保留触发条件、预期、实际结果和版本。会话已授权修复时使用可用的 `dev-workflow` 衔接开发，完成相关检查并重测原失败场景及受影响兼容场景后，按项目规则提交；记录修复前后版本。复验受阻时保留未验证状态，不把其他测试通过当作原失败已修复。未授权或超出范围时记录问题，继续不依赖它的验证，不自动扩大修改。其他场景的仍有效证据可以复用。

## 运行记录与模块知识

每次运行写入 `runs/<时间>-<主题>.md`，至少包含以下信息；短任务可以合并栏目：

```markdown
# 验证记录：<主题>

- scope/depth: <改动范围、业务目标、P0/变更验收、排除项>
- 版本: <各仓库路径、base、target 完整 hash、相关 dirty 与实际运行版本>
- 环境操作: <复用/启动的服务、实际目标、数据范围及授权限制>

| 场景 ID | 独立预期 | 实际结果 | 证据 | 状态 |
|---------|----------|----------|------|------|
| <ID> | <可核对结果> | <观察结果> | <截图/数据等链接> | <通过/失败/未覆盖/受阻> |

- 失败与修复: <复现、修复版本、重测证据，或无>
- 未覆盖/降级: <场景和原因；其他检查能证明与不能证明的内容>
- 沉淀: <模块/env 更新位置；历史补录证据缺口>
- 基线: <推进或不推进、限定覆盖及理由>
```

`modules/*.md` 按 [TEMPLATE.md](../TEMPLATE.md) 维护稳定入口、调用链、场景和判断依据；发现知识失效先核对原因，不直接假定页面改版。更新经验证的部分并链接 run，不把整次日志堆入模块文件。`last-verified` 只代表标明的场景与版本范围。

## 结论与基线更新

最终报告简述范围、版本、各场景结果、关键证据、环境操作及剩余缺口，并链接 run。

- 只有本次范围内必要验收场景全部通过且运行版本明确，才能声明“本次范围验收完成”并推进对应完整基线。
- P0 通过仅记录 P0 覆盖；有失败、受阻、未覆盖或仅降级证据时，完整验收基线不推进。已通过的局部场景可以记为有范围的证据，供后续按 [analysis.md](analysis.md) 核对复用，不能跳过余下场景。
- 用户接受已知问题或调整范围时保留原结果与原因，不把失败改成通过，不把缩小范围的完成表述成整批验收通过。
- 测的是含相关 dirty 的工作区时如实记录该状态；即使后来提交，未核实内容一致前不能把结果直接转成纯提交基线。
